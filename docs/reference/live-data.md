# Live data

- Driver positions and the display names supplied by Swofty’s Live State API, including the player’s name for human drivers. Names are shown as supplied, without splitting or reformatting. Choose either the full grid or your car and the nearest four cars. Nearest shows two ahead and two behind, shifting towards the available cars at either end of the grid.
- Only vehicles positively identified as racers by Live State are included. Safety cars and other non-racing vehicles are excluded, independently of their name or vehicle slot.
- A small team logo between position and driver, using Live State’s badge reference and image service. Catalogue teams and runtime My Team references use the same interface. Missing or pending images leave a blank cell without waiting for an image to load. Badges are displayed only once that row’s name, current position and tyre compound are known. Images preserve transparency and aspect ratio and stay in memory. Runtime capture is armed at add-on load and retried during startup, before entering a session, so My Team textures rendered in menus can be observed. While the table is gated during loading, available Live State racer references are used to request and poll badge images early, once per unique reference per pass. This prefetch never publishes driver rows or bypasses snapshot synchronization.
- Actual tyre compound labels with native coloured circles. Dry tyre colours use the current soft/medium/hard designation; intermediates are green and wets blue.
- A session label in the existing page subtitle: Practice 1/2/3, short practice, qualifying and sprint qualifying formats, Sprint, Race or Time Trial. Live State supplies the numeric type. Swofty’s session context distinguishes Sprint from Race; if that context is unavailable for the ambiguous race ID, the label reads **Race / Sprint (unconfirmed)**. Missing data stays **Unknown**. Session labels clear with the table when the session ends.
- Timed practice, qualifying and sprint qualifying sessions show the game’s remaining time as **MM:SS remaining**, when the verified ruleset getter is available. Sprint/race sessions show **Lap current/total** using the race leader’s progress and the current ruleset distance. Current lap comes from Live State; the remaining-time getter and total race distance use checked named bindings. Counters remain absent when unavailable; they do not use UDP or a locally simulated countdown.
- The session label and counters share the existing subtitle to avoid adding a separate block above the table. The launcher controls page scrolling; smaller windows, larger grids or open setup cards may still require it.
- Practice tables show Pos, team badge, Driver, Tyre, completed Laps, Last lap, Best lap, Status and Setup.
- Qualifying and Sprint Qualifying add Gap to best, calculated from the fastest valid lap across the entire current session, including cars outside a nearby-driver window. Known disqualified cars are excluded from that benchmark.
- Sprint and Race tables show Pos, positions gained/lost from the starting grid, team badge, Driver, Tyre, Gap ahead, Last lap, Best lap, S1/S2/S3, FL/FR/RL/RR/Avg wear percentages and Status. The three sectors belong to the same best valid lap; they are not individual sector records. Race tables have no setup controls. Laps on tyre are omitted.
- Status has its own column. DNF (did not finish or retired) and DSQ (disqualified) take priority over Pit; otherwise known results show Run, Finished or NC. Unavailable status remains a dash. DNF/DSQ rows use muted text, including the player's row; tyre colours and badges remain visible. The launcher table API does not expose whole-row opacity.
- Practice and qualifying retain the setup toggle and card beneath each driver, showing wings, differentials, camber, toe, suspension, anti-roll bars, ride heights, brakes, all four configured tyre pressures and fuel remaining. Unavailable readings show a dash. Fuel remaining is the current tank value, rather than the original setup fuel load.
- Last completed lap and best valid lap are shown in every layout. Unavailable readings stay as dashes. Zero completed laps and a known zero race interval remain valid values. Time Trial and unknown session types use the basic practice layout.
- Optional highlighting of your own row. Display settings are in Swofty's add-on settings.
- Driver, wear and lap-time columns automatically share the available width when the launcher is resized or maximised. Narrow windows can still truncate content; maximising gives these columns more room.
- The table stays empty at the career trackside workstation and during session loading/unloading. Values appear in the actual session's garage or grid. Pausing an active session retains current values. Session end/unload clears them; closing the game releases the shared snapshot.

## Processes and local files

Swofty starts **`telemetry-live.exe`**, a small background helper with no separate window. It communicates with Swofty through local input/output pipes. Swofty loads **`telemetry-live.dll`** inside the game using its normal native add-on system. The DLL uses Swofty 1.9.76’s Live State API for player identity, names, position, result status, session type, tyre compound, pit-lane status, per-car completed laps and gap ahead. CarOps supplies car count/handles, fuel, brake pressure and brake bias. The replaced private readers have been removed. Starting-grid positions and component pointers use Swofty’s exported type declarations. Wear, the remaining setup values, completed lap history and the missing session-ruleset fields retain checked direct readers. Two existing lap-timing functions are observed without changing their arguments or results. The add-on does not change car settings or game files.

Live State availability depends on Swofty's verified layouts for the running game build. Missing individual readings stay unknown. An unavailable or changing snapshot retains the last display until fresh data returns or the session ends; there is no private-reader fallback for API-covered values. The older telemetry API, which can include UDP data, is not used.

The DLL publishes a fixed **9,984-byte telemetry snapshot** and an optional **533,280-byte badge snapshot** in Windows. The badge buffer holds at most 32 images of up to 64 × 64 RGBA pixels. Both buffers share a publication sequence. The helper copies them under the same generation check and only commits a complete matched view; a concurrent update retains the previous view. Session end clears immediately even if the badge buffer is busy. The helper opens the buffers read-only and displays the latest matched values. There is no network listener, web server, separate recording process, Python runtime or installed Windows service. The add-on retains current values, a small timing cache and at most 32 encoded badge images. PNG conversion is reused while the image reference, dimensions and revision stay unchanged. Session and car identity checks prevent a previous session’s or replaced car’s badge appearing in a new row. No game resources are extracted to disk.

The helper exits when Swofty closes its communication pipe. Disabling the add-on clears its display and closes the helper's snapshot handles; Swofty may keep the helper process running. A native component already loaded in a running game remains there until that game closes. Restart the game after enabling, disabling or updating a native add-on.

v0.5.9 writes no telemetry files, images or settings of its own. Swofty manages its profile settings and normal launcher logs. Existing data in **Documents/F1 Game Telemetry** is left untouched, but this live-only version does not open or analyse those recordings. Nothing is uploaded by the add-on.
